# [已归档] 功能 8：结果资产与产物索引管理 V1 计划

## 目标

- 将任务执行结果中的文件、元数据、主产物判定和结果索引抽成独立功能域。
- 为功能 2、功能 4、功能 7 产出的不同结果建立统一的 `Artifact` / `ArtifactSet` 语义。
- 为功能 3 的任务查询、汇总和后续预览层提供稳定的结果资产结构。

## 背景

- 当前流水线与工具已经开始返回 `artifacts`，但这一层仍主要停留在“各执行器自己组织返回值”。
- 当前系统里已经能看到多种结果类型：
  - 混音成品
  - 字幕文件
  - TTS 音频
  - vocals / stems
  - transcript
  - 分析结果
- 如果不独立定义结果资产层，后面会持续出现这些问题：
  - 不同任务类型的结果结构不一致
  - 主产物判定规则散落在执行器或前端页面里
  - 任务成功但中间产物缺失时，系统无法稳定表达“为什么缺失”
  - 结果预览层被迫直接理解每类任务的私有输出格式

## 功能定位

功能 8 负责“结果是什么”和“如何被统一索引”。

它负责：

1. 定义统一结果资产模型。
2. 定义主产物与中间产物的判定规则。
3. 统一产物状态与缺失语义。
4. 为任务结果提供稳定索引结构。
5. 为后续预览、浏览、人工校对提供结果入口。

它不负责播放器 UI、本地打开文件按钮样式或完整人工编辑流程。

## 与其他功能的关系

### 与功能 2 的关系

- 功能 2 生产 `pipeline` 类型任务的结果。
- 功能 8 负责把这些结果收敛成统一 `ArtifactSet`。

### 与功能 4 的关系

- 功能 4 生产单工具任务的结果。
- 功能 8 负责统一这些工具结果的外层产物结构。

### 与功能 7 的关系

- 功能 7 负责字幕和脚本文本资产本身。
- 功能 8 只负责把这些字幕资产作为任务结果的一部分进行索引。

### 与功能 3 的关系

- 功能 3 记录任务结果引用和状态。
- 功能 8 定义“结果引用的结构到底长什么样”。

## 边界

### 本功能负责

- `Artifact` 模型定义
- `ArtifactSet` 模型定义
- `primary_output` 判定
- 产物类型分类
- 产物来源阶段标记
- 产物可用性与缺失语义
- 统一任务结果索引结构

### 本功能不负责

- 不负责具体业务执行，这属于功能 2、功能 4、功能 7
- 不负责统一任务调度，这属于功能 3
- 不负责播放、预览、波形或字幕查看器，这属于后续预览层功能
- 不负责完整人工校对工作流，只提供可供人工校对消费的结果入口

## V1 需要实现的功能

### 1. 统一产物模型

V1 至少定义：

- `Artifact`
- `ArtifactSet`
- `ArtifactReference`

其中 `Artifact` 建议至少包含：

- `artifact_id`
- `artifact_type`
- `path`
- `display_name`
- `source_task_id`
- `source_stage`
- `status`
- `metadata`

其中 `artifact_type` 至少覆盖：

- `audio.mix`
- `audio.tts`
- `audio.vocals`
- `audio.segment`
- `subtitle.srt`
- `subtitle.vtt`
- `subtitle.lrc`
- `text.transcript`
- `analysis.volume`
- `analysis.report`

### 2. 主产物判定

V1 需要给不同任务类型定义主产物规则。

例如：

- `pipeline` 任务默认主产物是最终混音或最终字幕输出
- `tool.asr` 任务默认主产物是 transcript 或导出字幕
- `tool.tts` 任务默认主产物是合成音频
- `tool.translate_subtitle` 任务默认主产物是译文字幕

这项规则应由功能 8 统一管理，而不是让每个页面自行判断。

### 3. 缺失语义与状态

V1 必须明确区分：

- 产物已生成
- 产物被跳过
- 产物理论上存在但执行失败未生成
- 产物不适用于该任务类型

建议统一状态：

- `ready`
- `skipped`
- `failed`
- `not_applicable`

### 4. 结果索引

V1 需要为任务结果提供统一索引结构，至少包括：

- `primary_output`
- `artifacts`
- `artifact_groups`
- `summary`

这样任务页、工作台、工具页不需要分别理解每个任务的内部返回格式。

## API 设计

### `GET /api/v1/tasks/{task_id}/result`

用途：

- 返回统一任务结果结构

### `GET /api/v1/tasks/{task_id}/artifacts`

用途：

- 单独返回产物清单

### `GET /api/v1/artifacts/{artifact_id}`

用途：

- 查询单个结果资产详情

### `GET /api/v1/artifacts/by-task/{task_id}`

用途：

- 按任务读取结构化产物索引

说明：

- V1 不要求一次性重构所有旧接口
- 但内部产物结构应逐步收敛到功能 8

## 中间层设计

### `ArtifactModelService`

职责：

- 定义和构建统一 `Artifact` 结构

### `ArtifactIndexService`

职责：

- 组织任务结果中的 `ArtifactSet`
- 维护主产物与分组索引

### `ArtifactPolicyService`

职责：

- 维护不同任务类型的主产物规则
- 维护产物状态和缺失语义规则

## 与当前实现的关系

### 可以保留的思路

- `ArtifactSet` 作为轻量产物集合的思路
- `PathPlanner` 对主产物与中间产物的目录分层经验
- 功能 2 中已经开始形成的结构化 `artifacts` 返回方向

### 必须重组或迁移的部分

- `artifacts` 不能继续只是执行器私有返回结构
- 主产物不能再由页面或调用方猜测
- 不同工具结果的外层结构需要被统一包装

### 明确不继承的历史包袱

- 不继承“结果就是一个路径字符串”的方式
- 不继承“主产物由页面临时猜”的方式
- 不继承“缺失产物不区分 skipped 和 failed”的方式

## V1 内必须落地

1. 统一 `Artifact` / `ArtifactSet` 模型
2. 明确主产物判定规则
3. 明确产物状态与缺失语义
4. 提供统一任务结果索引结构

## V1 内暂不落地

1. 不在这一轮做复杂资产版本管理
2. 不在这一轮做结果去重存储
3. 不在这一轮做跨任务产物依赖图

## 一句话结论

功能 8 可以正式定义为：

> 结果资产与产物索引管理 = 统一定义任务执行后产生的文件和分析结果，并为后续预览、浏览与人工校对提供稳定的结果入口。
