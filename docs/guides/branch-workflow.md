# 分支与发布约定

## 两条长期分支

- `master`：稳定主线，作为发布来源。开发改动完成验收后再合入。
- `dev`：当前集成和验收基线，承接跨模块修复及已准备整合的功能。

本次建立 `dev` 不代表创建正式版本。标签只标记实际发布，发布后不移动标签。旧版标签的本地与远程差异见 [2026-09-29 整理记录](../roadmap/git-baseline-cleanup-2026-09-29.md)。

## 一个任务一个临时分支

从最新 `dev` 创建 `feature/功能名`、`fix/问题名` 或 `codex/任务名`。任务从实验扩大为通用修复时，把通用修复独立提交并及时合入 `dev`，后续实验继续在任务分支进行。

```powershell
git switch dev
git pull --ff-only
git switch -c fix/example
# 修改、验证、提交后
git switch dev
git merge --no-ff fix/example
git push origin dev
git branch -d fix/example
```

多人协作时通过 PR 合并。合并前核实相关测试、前端构建和实际功能；涉及模型和外部供应商时，区分模拟测试与真实推理验证。删除远程分支前检查是否有其他人在用、是否有开放 PR。

## 发布

1. 在 `dev` 收敛本次交付范围，完成回归和产品验收。
2. 将 `dev` 正常合并到 `master`；遇到主线独有修复时先同步回 `dev` 验证。
3. 统一需要发布的组件版本，记录变更与限制，再建立新标签并发布。
4. 清理已合并任务分支。未合并的历史工作先归档保存，不能仅因分支名称旧就判定可以丢弃。

提交历史继续保留；分支数量减少不需要重写过去的提交。
