# 当前分支修复基线计划

## 目标

- 以当前 `refactor/re-design` 分支作为新的正式修复起点。
- 将“前端来自 backup”视为已确认事实，不再把 `desktop/` 视为异常漂移。
- 重新整理当前分支现状，为后续修复确定明确基线。

## 背景

- 当前用户已确认：前端骨架就是从 backup 拉取到当前分支的。
- 因此当前分支的核心问题不再是“前端是否误入”，而是：
  - 后端收口改动未完整留在当前分支
  - `docs/` 历史文档未留在当前分支
  - `script_subtitle_service` 相关测试仍存在套件级污染
- 需要从当前分支重新开始推进，而不是继续把历史对话中的状态默认视为已落地。

## 步骤

1. 记录当前分支的 Git、目录、代码和测试现状。
2. 明确当前分支与 backup 分支的角色分工：
   - 当前分支：新的主修复线
   - backup 分支：历史参考与内容来源
3. 识别当前分支后续优先修复项：
   - `tests/test_script_subtitle_service.py` 套件污染
   - `docs/` 缺口补齐
   - HTTP / DTO / task / artifact 契约重新收口
4. 写入任务日志，作为后续修复工作的共同起点。

## 验证

- 能明确说明当前分支哪些内容是保留现状，哪些内容需要重新修复。
- 能明确说明当前测试不稳定点与后续优先级。

## 风险

- backup 分支中的历史文档和修复记录并不自动等于当前分支已落地内容。
- 若后续需要从 backup 摘回内容，仍需逐项核对，避免把旧状态直接覆盖到当前分支。
