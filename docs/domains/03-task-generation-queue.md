# 功能 3：统一任务生成与任务队列 V1 计划

## 目标

- 建立整个项目统一的后台任务系统，而不是让 Workbench、Batch、Tools 各自维护局部任务状态。
- 明确任务生成、任务入队、任务调度、执行器分发、取消重试、结果追踪的职责边界。
- 让完整流水线任务与单步工具任务进入同一个队列体系，避免形成多套并行任务机制。

## 背景

- 当前 `TaskService` 只是一个进程内存状态表，只覆盖 `pending/running/completed/failed` 等最基础状态。
- 当前 `PipelineService` 在自己创建 task，说明任务生成和任务执行尚未拆开。
- 当前 `BatchPipelineService` 是“循环调用单文件 pipeline”的实现，不是真正的任务生成器加任务队列。
- 当前桌面前端 `Tools.tsx` 也在本地自行创建 task 视图对象，说明小工具任务尚未进入统一后台任务体系。
- 经边界确认后，系统需要一个统一的任务中心来接收来自流水线和小工具的后台任务请求。

## 功能定位

该功能域是整个系统的任务中枢。

它负责：

1. 将用户动作或批量规划结果转换为标准任务定义。
2. 将任务写入统一队列。
3. 管理任务状态机与生命周期。
4. 将不同 `task_type` 分发到对应执行器。
5. 提供统一的查询、取消、重试和队列快照能力。

它不直接实现具体业务处理逻辑。

## 边界

### 本功能负责

- 单任务生成。
- 批量任务生成。
- 任务入队与出队。
- 并发控制与执行器分发。
- 任务状态、进度、错误、结果索引的统一管理。
- 取消、重试、跳过等任务级动作。

### 本功能不负责

- 不负责输入文件识别、输出目录规划，这些属于功能 1。
- 不负责完整流水线业务处理，这些属于功能 2。
- 不负责单步工具业务处理，这些属于功能 4。
- 不负责页面展示层样式和交互布局。

## V1 需要实现的功能

### 1. 标准任务定义

系统需要建立统一的 `TaskSpec`，用于表示“一个后台任务应该如何运行”。

V1 任务定义至少应包含：

- `task_id`
- `task_type`
- `task_source`
- `session_id`
- `input_asset_id`
- `companion_asset_ids`
- `execution_profile`
- `priority`
- `dedupe_key`
- `created_at`

V1 支持的任务类型至少包括：

- `pipeline`
- `tool.separate`
- `tool.asr`
- `tool.translate_subtitle`
- `tool.tts`
- `tool.split`
- `tool.convert`
- `tool.script_to_subtitle`
- `tool.volume_preview`

说明：

- 字幕相关 `task_type` 同样进入功能 3 的统一队列。
- 但其业务语义、字幕数据结构与处理规则归属功能 7，而不是功能 3。

`execution_profile` 的职责是冻结“这次任务实际要怎么跑”，但不携带敏感凭据和运行时资源。

V1 需要明确：

- `TaskSpec` 内保存 `ExecutionProfile`
- `TaskSpec` 不保存 `RuntimeBinding`
- API key、base URL、本地模型实际路径等敏感或环境相关内容只在执行阶段注入

### 2. 单任务生成

系统需要支持从单一用户动作生成一个标准任务。

V1 适用场景：

- Workbench 创建一个完整流水线任务。
- Tools 创建一个单步工具任务。

V1 要求：

- 单任务生成与立即执行解耦。
- 生成阶段只负责固化参数，不负责真正运行。

### 3. 批量任务生成

系统需要支持从多文件或文件夹输入中批量生成多个标准任务。

V1 要求：

- 每个输入文件拆成一个独立任务。
- 多个任务共享参数，但任务自身独立固化。
- 允许在生成阶段执行去重、跳过已有输出等规则。

V1 批量生成器不直接调用 pipeline 或工具执行器，而是只输出任务并入队。

### 4. 统一队列

系统需要维护单一任务队列，而不是“流水线一套、工具一套”。

V1 队列至少应支持：

- `draft`
- `queued`
- `running`
- `completed`
- `failed`
- `cancelled`
- `skipped`

V1 行为至少应包括：

- 入队
- 出队
- 查询队列
- 并发控制
- 取消
- 重试
- 跳过

### 5. 执行器分发

任务系统不直接做业务执行，而是根据 `task_type` 分发给对应执行器。

V1 分发关系建议：

- `pipeline` -> 功能 2 的编排执行器
- `tool.*` -> 功能 4 的对应工具执行器

V1 至少要建立统一的注册表或映射机制，而不是通过 if/else 在多处硬编码。

### 6. 任务结果追踪

系统需要统一维护任务记录和任务结果。

V1 任务记录至少应包含：

- `task_id`
- `status`
- `progress`
- `message`
- `detail`
- `worker_id`
- `queued_at`
- `started_at`
- `finished_at`
- `retry_count`
- `error_code`
- `error_message`

V1 任务结果至少应包含：

- `task_id`
- `success`
- `artifacts`
- `warnings`
- `error_message`
- `duration_seconds`

## 对外 API 设计

### `POST /api/v1/tasks`

用途：

- 创建一个任务并入队

### `POST /api/v1/tasks/batch`

用途：

- 一次创建多个任务并批量入队

### `GET /api/v1/tasks`

用途：

- 查询任务列表

### `GET /api/v1/tasks/{task_id}`

用途：

- 查询单任务详情

### `GET /api/v1/tasks/{task_id}/result`

用途：

- 查询单任务结果

### `POST /api/v1/tasks/{task_id}/cancel`

用途：

- 取消一个任务

### `POST /api/v1/tasks/{task_id}/retry`

用途：

- 将失败或取消任务重新入队

### `GET /api/v1/task-queue`

用途：

- 获取统一队列快照

## 中间层设计

### `TaskSpecFactory`

职责：

- 从 session 或工具动作生成标准任务定义
- 支持单任务与批量任务生成
- 从功能 6 读取 `CapabilityDescriptor`
- 生成并冻结 `ExecutionProfile`

### `TaskQueueService`

职责：

- 管理任务状态机
- 入队、出队、取消、重试
- 维护队列快照

### `TaskDispatcher`

职责：

- 根据 `task_type` 将任务分发到正确执行器
- 管理执行器调用生命周期

### `TaskResultService`

职责：

- 汇总任务结果
- 提供结果查询与索引能力

## 与当前实现的关系

### 可以保留的思路

- `TaskService` 中基础的任务状态表思路可以保留，但需要升级为完整队列模型。
- `BatchPipelineService` 中多文件输入拆分经验可以保留，但要从“直接执行”改为“生成任务并入队”。
- 前端已有的任务列表展示形态可以保留为 UI 参考，但不能继续作为任务系统事实来源。

### 必须重写或重组的部分

- `TaskService` 当前只适合做轻量状态对象存储，不足以承担统一队列职责。
- `PipelineService` 当前自己创建 task，需要迁移为“消费任务”的执行器。
- `BatchPipelineService` 当前是同步执行器外壳，需要迁移为批量任务生成器。
- `Tools.tsx` 当前本地生成任务对象，需要迁移为调用统一任务创建接口。
- 当前任务模型尚未区分“参数冻结”和“运行时注入”，需要拆分为 `ExecutionProfile` 与 `RuntimeBinding`。

### 明确不继承的历史包袱

- 不继承“pipeline 任务自己在执行器内创建”的方式。
- 不继承“工具页单独维护本地任务列表”的方式。
- 不继承“批处理就是循环调用执行器”的方式。
- 不继承“只有流水线任务才算后台任务”的方式。

## 具体实现范围

### V1 内必须落地

1. 定义统一任务模型。
2. 建立统一任务状态机。
3. 实现单任务与批量任务入队。
4. 实现执行器分发机制。
5. 让 `pipeline` 任务与主要 `tool.*` 任务都进入同一队列。
6. 提供统一查询、取消、重试接口。

### V1 内暂不落地

1. 不在这一轮做复杂优先级调度。
2. 不在这一轮做跨进程恢复。
3. 不在这一轮做分布式执行。
4. 不在这一轮做任务依赖 DAG。
5. 不在这一轮要求完整持久化仓储，但模型设计应为长期方案预留。

## 风险与注意事项

- 如果功能 3 不先建立清晰边界，功能 2 和功能 4 会继续各自偷偷持有任务逻辑。
- 如果任务类型命名不统一，后续执行器分发会持续混乱。
- 如果不把小工具任务纳入统一队列，任务中心最终只能覆盖部分后台能力，难以成为系统中枢。

## 验收标准

- 完整流水线任务和单步工具任务都能进入同一任务队列。
- 批量任务生成只负责生成与入队，不直接做业务执行。
- 任务状态机统一，且能支持取消、重试、跳过。
- 功能 2 和功能 4 都作为功能 3 的执行器消费者接入，而不是各自维护独立队列。

## 与现有文档的关系

- 本文档是“功能 3：统一任务生成与任务队列”的上游计划文档。
- 它在功能 1、功能 2 与功能 4 之间建立后台任务系统的中心边界。
- 后续进入实现阶段时，应新增执行日志，避免再将批量拆分、任务调度、业务执行混写。
